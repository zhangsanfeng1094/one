# 权限控制与工具任务审查

审查日期：2026-09-19。范围：当前工作区实现，包含未提交修改；不是仅审查某次提交。采用静态代码追踪，未运行测试、未执行攻击验证，也未修改业务代码。以下区分明确的控制流问题与设计优化建议。

## 结论

优先修正权限判定的顺序和路径规范化，其次把授权清理从扩展钩子中独立出来，再改进任务句柄和调度边界。已有 PathPolicy、沙箱、子任务协调器可以继续沿用，无需整体重写。

## 1. P1：普通 allow 规则绕过沙箱升级和内置危险命令检查

位置：`crates/one-tools/src/permissions.rs:650`、`:684`、`:691`、`:699`；`crates/one-cli/src/approval.rs:514`。

`evaluate_with_mode` 命中 allow 后立即返回；禁止命令、强制确认及 `require_escalated` 检查全部位于后面的默认判定中。Bash 规则匹配只看 command，不区分是否请求解除沙箱（`permissions.rs:201`）。因此，在 bwrap 可用、默认权限模式下，同一个 allow 规则可以批准沙箱内命令及其脱离沙箱的版本；宽泛规则还可跳过内置危险命令检查。这与代码中“沙箱升级需要 Ask”“破坏性命令始终确认”的约束不一致。

建议：拆成不可跳过的安全约束、显式 deny、授权规则三层。普通 allow 只授权命令，不隐含脱离沙箱的能力；为 escalation 设置独立授权域。会话缓存也应遵守相同约束。

回归用例：为某命令配置 allow，分别提交 use_default 和 require_escalated，后者必须单独审批；宽泛 Bash allow 不能跳过硬性禁止和强制确认。

## 2. P1：路径 deny 规则可以被等价路径拼写绕过

位置：`crates/one-tools/src/permissions.rs:207`、`:223–234`；`crates/one-cli/src/approval.rs:514`、`:648`。

规则直接匹配原始 path 字符串，只对绝对路径额外做后缀匹配，没有先解析 `.`、`..` 和实际路径。例如 deny `Read(.env)` 能匹配 `.env`，但不能匹配相同文件的 `./.env`。后续 PathPolicy 检查负责根目录边界，工作区内文件仍然通过，无法补上文件级 deny。符号链接别名也需要统一考虑。

建议：在权限规则前统一解析工具参数别名和相对路径，以执行时 cwd 得到规范化目标；让规则检查与工具执行使用同一目标。保留用户原始路径用于展示。对于新建文件，规范化已存在的父目录，再附加文件名。

回归用例：同一文件通过 `.env`、`./.env`、`sub/../.env`、绝对路径及符号链接访问时，deny 结果一致。

## 3. P1：一次性授权回收依赖可超时的扩展钩子

位置：`crates/one-core/src/agent.rs:1679` 附近；`crates/one-ext/src/runtime.rs:367–369`；`crates/one-cli/src/approval.rs:652–665`；`crates/one-tools/src/path_policy.rs:534–544`。

核心把 after_tool 放入后台任务，并对整个钩子链设置 5 秒超时。扩展包装器先等待扩展 after_tool，再调用权限 gate 的 after_tool；一次性 token 正是在后者中回收。如果扩展超过 5 秒或不返回，权限清理就不会执行。PathPolicy 检查 token 时只查找、不消费，所以授权记录会残留。另一个遗漏是已审批但执行前发现 abort 的分支，直接返回而不清理。

这是授权生命周期问题；尚未验证外部调用方是否能获得并重放残留 token，不将其描述为已验证的任意越权。

建议：把安全资源释放从观察性钩子中拆出，使用执行作用域持有的 RAII guard，在成功、失败、取消和未执行时均回收。遥测及扩展钩子可以继续异步限时。不要简单在首次路径校验时消费 token，工具内部可能需要多次检查同一授权。

回归用例：扩展永不返回、执行取消、审批后取消时，once 授权集合均恢复到调用前状态。

## 4. P2：前台任务的工具绑定建立得太晚

位置：`crates/one-cli/src/runtime/task_tool.rs:576–618`；`crates/one-cli/src/runtime/coordinator.rs:395–412`。

TaskTool 先等待 coordinator.spawn，再绑定 tool_call_id → job_id。对于已经开始的前台任务，协调器直到任务完成才返回；此时绑定刚建立就被删除。因此运行中无法通过该映射查询前台任务，与 `job_for_tool` 的运行中查询用途不符。交互界面还有 job 列表兜底刷新，所以不能据此断言全部进度显示失效。

建议：拆分“提交并返回句柄”和“等待完成”。注册后立即返回含 job_id、完成通知和取消能力的句柄，TaskTool 先绑定，再按前后台模式决定是否等待；结束时统一解绑。

回归用例：用阻塞的测试 provider 启动前台任务，在放行 provider 前断言 job_for_tool 已返回对应任务，结束后绑定消失。

## 5. P2：只读工具批次没有并发上限

位置：`crates/one-core/src/agent.rs:1463`、`:1717` 附近。

连续只读工具全部推入 FuturesUnordered，没有执行并发阈值。批量 grep、目录扫描或读取大文件时，资源峰值随模型返回的工具数量增长。现有串行副作用工具策略是合理的，但只读不代表资源消耗低。

建议：使用可配置的有界并发，保留现有按完成顺序发 UI 事件、按原始顺序记录结果的行为。后续将“是否可并行”从工具名白名单升级为工具元数据，并明确文件写入、共享 shell 状态等冲突域。

回归用例：提交超过上限的阻塞工具，验证峰值执行数、取消排空和结果顺序。

## 后续结构优化

- **统一授权决策对象**：包含原因码、命中规则、策略版本、作用域、是否解除沙箱；避免 UI 和执行逻辑解析 reason 字符串。审批缓存绑定 cwd、有效参数、授权域及策略版本，策略收紧时失效。
- **任务执行上下文**：统一传递 run_id、call_id、取消信号、deadline 和授权租约。审批等待、排队、执行、后置观察分别计时，便于解释任务卡在哪里。
- **预编译权限规则**：当前每次判定都会分配三个规则列表并重新 parse。配置加载时编译并报告无效规则，运行时直接匹配；权限热更新时原子替换快照。
- **子任务权限上限显式化**：将父级上限与子级请求权限求交，写入任务记录，便于审计权限继承。此次未完成所有工具/MCP 继承路径的验证，属于设计建议，不能视为已证实的继承漏洞。

建议实施顺序：先处理 1、2 并补权限矩阵测试；再处理 3 的清理机制；最后实现 4 的任务句柄和 5 的有界调度。
